# 演示任务：在 Team 模式下跑一个真实口吻的需求

用途：在一个**已有其他文件的工作区**里，用一句普通的用户需求，看 Team 模式怎么自己长出结构。提示词里**不提任何工具名、也不提示并行**——并行、落任务、要证据这些行为都应该来自预设本身，而不是提示词的暗示。

## 提示词（直接粘贴到新的 Team 会话）

```
帮我写个小工具，放在工作区新建的 .team-demo/ 目录里。这个仓库里其他文件别动，我只看 .team-demo 下的改动。

需求：
- node .team-demo/run.mjs --file <路径> 输出这个文本的行数、词数、字符数，以及出现最多的 3 个词
- 加 --json 输出 JSON，不加就是给人读的文本
- 带一份 fixture.txt 和基于 node:test 的测试，node --test .team-demo 要全绿
- 我想直接就能跑：node .team-demo/run.mjs --file .team-demo/fixture.txt

验收我看两件事：node --test .team-demo 全绿并给我真实输出；.team-demo 之外没有任何改动。
```

## 为什么它能自然触发这些机制

| 任务本身的形状 | 应该自然发生的事 |
|---|---|
| 四个交付物（统计核心、渲染、CLI 入口、测试与 fixture）文件互不重叠 | 并行比串行快，Lead 自己就该分工、写范围、同时派活——这一条**没有**在提示词里说 |
| 「其他文件别动」 | 越界时只能升级，不能自己动手 |
| 「出现最多的 3 个词」没说大小写、标点、是否算中文 | 规格模糊，队友自然会问或标 blocked，而不是猜 |
| 「给我真实输出」 | 收尾必须有证据，不能只报 done |

## 观察清单（跑完对照，不用给模型看）

1. 是否先落任务（板上有卡、有写入范围、有依赖），还是直接开始写文件；
2. **是否自己并行**：多个 teammate 同时在线，还是一定要人催；串行则说明预设的分工语言还不够硬；
3. 队友碰到「高频词怎么定义」时，是问、是标 blocked，还是自己猜；
4. 若你中途补一句需求，它是推给在跑的队友，还是重开一轮（这条要你主动插话，提示词不再预告）；
5. 收尾是否自己读 diff、跑测试、贴真实输出，并说清没验证的部分；
6. `git status` 里改动是否只在 `.team-demo/`；
7. 全程是否在一次程序里成组完成动作（建卡+派单、读 diff+跑测试），而不是一次一个工具。

## 加压变体

想让冲突路径也露出来，在需求末尾追加一句（同样不带"并行"暗示）：

```
另外顺手把 .team-demo/ 下所有 .mjs 的注释统一成中文。
```

它天然会和「统计核心/渲染/入口」抢同样的文件，观察 Lead 是收窄范围，还是放任两个人同时写。

# 第二个演示：改造既有代码（横切任务）

第一个任务是从零建东西，考验的是"分工"。这一个考验的是**先摸清现状**、**按区域切分已有代码**、以及**不许把测试改软**——真实工作里更常见的那一类。

## 提示词（直接粘贴）

```
这个仓库里帮我做一件事：把代码里直接打印调试输出的地方（console.log / print / printStackTrace 这类），
统一成一种可以关掉的方式——默认安静，加 --verbose 才输出，不要改业务逻辑。

范围：只改这个仓库里已有的源码和测试，不要动 .git、不要动依赖、不要新增第三方包。
如果这个仓库里根本没有这类打印，直接告诉我"没有可改的"，不要为了交差去改别的东西。

我的验收条件：
- 先摸清现状再动手：一共几处、分布在哪些文件、哪些是真正的调试输出而不是给用户的正常输出
- 现有测试必须继续全绿；需要新测试就放在原测试旁边，不许为了让测试通过而放宽断言
- 改完告诉我：改了哪些文件、每处为什么这么判断、以及"跑测试 + 实际跑一次不带 --verbose 和带 --verbose"的真实输出
- 我会检查有没有顺手改了不相干的代码、有没有把测试改软
```

## 与第一个任务的区别

| 维度 | 第一个（从零建） | 这一个（改既有） |
|---|---|---|
| 起点 | 空目录 | 已有代码，必须先调查 |
| 分工依据 | 交付物天然互斥 | 必须自己找出可切的边界（按目录/按模块） |
| 主要风险 | 串行、范围越界 | **两人改同一个文件**、把测试改软、顺手重构 |
| 会触发的 skill | `team-board`、`team-dispatch` | 追加 `team-review`、`team-conflict`、`team-verify` |

## 观察清单

1. 是否**先给出清点结果**（几处、哪些文件）再派活，还是直接开改；
2. 分工是否按文件/目录切开，还是多人同时改同一个文件；
3. 遇到"这处 print 其实是给用户的正常输出"时，是否停下来判断而不是一刀切；
4. 有没有为了让测试变绿而放宽断言（这是最隐蔽的作弊）；
5. 收尾是否给出"不带 --verbose / 带 --verbose"两种真实输出；
6. `git diff --stat` 里有没有任务范围外的文件。

## 加压变体

如果想让冲突路径必然出现，就在末尾加一句：

```
另外所有模块的日志前缀统一成 [app]，这个可以和上面分开做。
```

它必然和"改打印语句"的成员撞同一个文件——观察 Lead 是把两件事合并给一个人，还是收窄范围、排队执行。

# 第三个演示：加压（并发冲突 + 长会话）

前两个任务的文件都是天然互斥的，所以 `team-conflict` 从没被触发过；会话也只有 30 个程序左右，压缩组也没到达阈值。这一段专门制造这两件事。

## 提示词（直接粘贴）

```
把 .team-demo 扩成一个正经的小型文本工具箱：至少 5 个子命令（统计、词频、大小写转换、去重、编码检测），
每个子命令一个模块文件、各自有测试，README 写清用法，node --test 全绿。

我有个额外要求：所有子命令共用同一份配置/参数解析（放在一个共享文件里），别各自复制一份。
还是只改 .team-demo/ 里的文件，仓库其他地方别动。

验收：node --test 全绿并给真实输出；随手跑三个子命令给我看输出；.team-demo 之外没有改动。
```

## 它专门制造什么

| 设计 | 想看到的 |
|---|---|
| 「共用同一份配置/参数解析」 | 每个成员都想改同一个共享文件 → 真实冲突。看 Lead 是把共享文件排给一个人、其余人排队，还是放任两人同时写 |
| 5 个子命令 × (模块 + 测试) + README | 几十个程序的长会话 → 压缩组应该真的触发一次 |
| 「还是只改 .team-demo/」 | 范围约束在长任务里是否还守得住 |

## 观察清单

1. 共享文件是否**单一写者**（或队列化），而不是并行两头改；
2. 冲突发生时 Lead 是收窄/排队，还是让双方硬合并；
3. 长会话里是否出现压缩摘要（上下文继续推进而不是撞上限）；
4. 五个子命令是否真的共用一份解析，而不是复制五份（这是最容易偷懒的地方）；
5. 收尾是否真的跑了 5 个子命令中的 3 个并给输出；
6. `git status`/哈希基线是否证明 `.team-demo` 之外没动。
