# 演示任务：一次把 Team 模式与 DSH 原生件全用上

用途：在一个**已有其他文件的工作区**里跑一次 Team 模式，用可核对的产物展示「结构强制协作」到底长什么样。任务只在工作区内新建一个 `.team-demo/` 目录，其余文件只读。

## 任务提示词（直接粘贴到新的 Team 会话）

> 在本工作区里从零搭一个**文本统计 CLI**，只允许写 `.team-demo/` 目录，工作区里其它文件一律只读（不要格式化、不要重排、不要"顺手"改注释）。如果发现必须改外部文件才能完成，停下来用 `team-report` 的方式升级给我，不要自己动手。
>
> 交付目标：`.team-demo/run.mjs --file <path>` 能对给定文本输出**行数、词数、字符数、出现频次最高的 3 个词**，默认给人读的文本，加 `--json` 时输出 JSON；`.team-demo/` 下还要有 `fixture.txt` 和基于 `node:test` 的测试，`node --test .team-demo` 必须全绿。
>
> 硬性流程要求（这是验收条件，不是建议）：
> 1. 动手前先建任务板：用 `team_task_create` 至少建 4 张卡——「词法/统计核心」「报表渲染」「CLI 入口」「测试与 fixture」——每张卡写明**写入范围**（具体文件路径），入口卡用 `blocked_by` 依赖前两张。
> 2. 「词法/统计核心」「报表渲染」「测试与 fixture」必须**并行**：在同一条消息里同时派 3 个 teammate（各自 `name` 与 `description` 明确），不要串行等待。
> 3. 每个 teammate 只能写自己卡上声明的文件；任何人碰别人的文件即为失败。
> 4. 我会在第 2 步之后插一条变更（例如新增 `--min-length` 过滤，或改一个输出字段名）。你必须用 `send_message` 把变更推给**正在跑**的 teammate，不允许重新派单、也不允许自己动手改他们的文件。
> 5. 如果某个 teammate 收到的是含糊或信息不足的任务，它应该报告 `blocked` 并说明缺什么，而不是猜；你收到 `blocked` 后要么补规格、要么收窄范围。
> 6. 收尾必须按证据验收：你自己读 diff（不要拿 teammate 的 FINDINGS 当结论），跑 `node --test .team-demo` 与一次真实 CLI 调用，答复里给**命令 + 实际输出**，并说明哪些没验证。
> 7. 全程用 `run_code` 组织动作：一次程序里完成「建卡 + 派单」或「读 diff + 跑测试」，不要一次只调一个工具。

## 评分细则（跑完对照看）

| 期望看到 | 属于哪一层 |
|---|---|
| 任务板上有 4 张卡、带写入范围、`blocked_by`、状态流转到 completed | Agent Teams（DSH 原生） |
| 同一消息派出 3 个 teammate，名字出现在 roster，可 `interrupt_agent` | subagent / subagent_fork |
| 变更通过 `send_message` 推给在跑的队友；至少一次 `wait_agent` 收结果 | 团队消息通道 |
| 至少一次 `blocked` 升级 → Lead 补规格或收窄范围 | `team-report` playbook |
| Lead 自己读 diff 并给出打回/接受结论 | `team-review` / `team-verify` playbook |
| 一次「建卡 + 派单」或「读 diff + 跑测试」在一次 `run_code` 里完成 | PTC 执行器 |
| 冲突处理：两人同文件时按 `team-conflict` 收窄而不是硬合并 | `team-conflict` playbook |
| 最终改动只在 `.team-demo/` 内，工作区其它文件 `git status` 干净 | 写入范围约束 |
| 答复含命令与实际输出，并列出未验证项 | 证据标准 |

## 变体

- **最小版**（5 分钟）：去掉「测试与 fixture」和变更注入，只留 2 张卡 + 1 次并行派单，用来验证预设与任务板是否正常。
- **加压版**：让两张卡的写入范围**故意重叠**一个文件，观察 Lead 是否按 `team-conflict` 收窄范围，而不是让两人同时写。

## 说明

- 任务故意要求「只写 `.team-demo/`」，因为工作区可能还有别的文件：这条约束同时演示**写入范围**与**越界升级**两个行为。
- 第 4 条的变更注入需要人配合（在会话里发一句变更），这是刻意设计：它检验的是 `send_message` 的用法，而不是模型自觉。
